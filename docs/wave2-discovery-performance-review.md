## Hot path vs inventory

- Original GameDetector already queries foreground HWND and cached known games; known-game refresh interval ten minutes. Broad candidate Recorder.StartPolling uses two-second timer, TryEnter gate; GameDetector.DetectForeground queries HWND/PID/start time/executable and cached known games, not all executable files. GameCatalogRuntime.Match caches a path-index keyed to immutable settings instance; lock protects rebuild and lookup. CatalogIndex uses dictionary, explicit deny and exact identity. Managed code is already JIT-compiled; Rust would not magically speed Windows process queries, registry/disk/JSON IO or GPU encoding.
- Legacy active-audio path Recorder.Poll enumerates process snapshot for routing; selected-endpoint mode returns before that work. Attribute this separately from game detection. Avoid changing audio behavior for benchmark.
- GameDiscoveryCoordinator refreshes every 15 min, serial source worker, default 12 segments/250ms admission slice, 250ms delay between slices; snapshot throttle approximately one second. Source enable/disable and root settings trigger selective work. Filesystem/metadata access bounded per request; not a guarantee of total I/O latency (a single synchronous operation or snapshot may exceed admission budget). Providers are local metadata, no new runtime package. Inventory breadth does not imply each game is polled every two seconds.

## Potential hotspots, measure before changes

1. GameCatalogRuntime.Match lines 49–65 rebuilds projected catalog and dictionary inside gate on first match after settings reference changes. ScanPreview/Summarize may create frequent new references. Profile cold, steady unchanged, refresh and scan-preview invalidation, measure lock duration and capture/authorization latency. Do not reuse stale permission index; any optimization must atomically publish versioned immutable authorization state and fail closed. Check whether display-only scan preview can avoid active-index rebuild.
2. CatalogClaims.Rows/Project sorts/merges current claims, aliases, legacy/cache/manual rules, plus snapshot creation; summary and UI may recompute. Count projections, allocations, sorting costs and retained cache size at 100/1k/10k fixtures with overlapping providers and stale metadata. Avoid keeping duplicated large projections without evidence.
3. Source scanner admission checks are cooperative; slow filesystem operation, decompression, hashing, full manifest and executable tree/registry work can exceed slice budget. Test unavailable/slow drives and catalog with lots of helper files; verify cancellation/backpressure and no UI stalls. Compare periodic warm rescans to explicit incremental scan. Consider metadata fingerprints/invalidations or longer refresh only with correctness tests and user approval.
4. KnownGames refresh inside foreground path every ten minutes may access metadata; measure separately at refresh boundaries. Stable foreground process identity memoization only if lifetime/PID reuse/revocation checks preserved.
5. GameCatalogRuntime uses lock and exclusions linear in root count; hash lookup itself likely not expensive. Measure rather than introduce Rust/FFI or cache unsafe decisions. Distinguish armed no-game from source scan and active recording.

## Benchmark design

Use existing fixture injection and pure managed tests in separate research lane: sustained repeated catalog match (hits/misses/vetoes), 100/1k/10k game entries, warm steady vs identity replacement, p50/p95/p99, allocations, measured real CPU; avoid dead-code-eliminated constant loops, consume results, warm JIT and repeat. Capture scanner elapsed/CPU/IO/allocations using synthetic files, no production inventory. For owner test separately measure idle/master off, armed no game, user-triggered scan and active game during scan with current/baseline builds. Compare default configurations separately from matched workloads, and keep catalog size/launchers enabled comparable for v1.1 vs Wave2 where possible. Original stock lacks the same catalog and standby model: report functionality differences. Set no arbitrary performance claims or thresholds before collecting baseline. Profile only if measurable cost then fix highest-impact IO/rebuild issues in C# first. A Rust proof only makes sense if measured CPU-heavy isolated parser/index bottleneck remains after algorithmic correction. No architecture rewrite approved.
