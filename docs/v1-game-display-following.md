# Game display following

QuickClip Personal waits for a verified, eligible game while Instant Replay is enabled. The game window's owner includes its HWND, thread, PID and process creation time. Windows maps that window to the display with the largest intersection. An off-screen or minimized game has no active capture source. A foreground change to Discord leaves a still-observable game associated with its replay.

**Capture scope.** Desktop Duplication reads the game display, subject to the configured crop. Other visible apps and notifications can appear in clips. One explicit grant allows game-triggered capture on whichever connected display contains the game, including displays connected later. Existing single-display grants remain scoped to their original physical identity. Profiles previously set to manual-only wait for explicit game display permission. The manual desktop override has separate, temporary permission for one selected physical display. Stopping it returns to game detection. Turning the master off clears the manual grant.

The native DDA path uses FFmpeg's `ddagrab` on a named DXGI output with a verified Windows monitor device path. Personal uses monitor-only DDA. The separate `gfxcapture` path can capture an HWND or HMONITOR and is retained for the existing Upstream behavior. The Personal path leaves Windows Graphics Capture and its capture border settings alone. Windows requires separate consent and package capability for borderless WGC. [Desktop Duplication API](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api) · [WGC capture border requirements](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession.isborderrequired) · [MonitorFromWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-monitorfromwindow)

**Replay boundaries.** A game moving to another physical display, a game identity change, or switching between manual and automatic capture stops the previous engine and clears its unsaved replay and markers. The next engine starts with an empty ring, a new session ID and a fresh keyframe even if both displays use the same encoder format. A stale save request cannot be applied to the new engine. A replay already snapshotted for muxing can finish on its original session. A same-source repair can retain the buffer when its format is compatible. If native video observes that the game left the bound output, it invalidates that graph, even if the game returns before the recorder's next poll.

**Hotplug.** When an active game display disappears, capture pauses instead of following Windows' automatic window relocation. Reconnecting the original display lets the recorder verify the current game location again. Closing and relaunching the game also clears the disconnect state. A disconnected manual display stays unavailable until it returns or the override is changed. Ambiguous cloned outputs cannot establish a physical display identity.

## Simultaneous display capture

Use active Windows Display Configuration paths for the selector and draw monitor rectangles in one scaled physical-pixel coordinate space. Translate the layout by the minimum left and top so monitors at negative coordinates remain selectable. Use DPI-aware rendering for labels and hit targets in WPF. Per-monitor DPI affects UI layout while native capture and crop use physical pixels.

- **Stitched canvas.** Choose a shared canvas size, fit each output without distortion, and leave gaps or letterbox as needed. Handle mixed sizes, rotations and refresh rates explicitly. Compose on the GPU and check maximum texture size, hardware encoder dimensions and pixel throughput. Each output still needs its own capture session, and displays on different adapters may require a transfer before composition.
- **Independent video streams.** Preserve per-display resolution and aspect ratio. Budget one capture and potentially one encode session per display. Decide whether the editor and export support multi-video containers or separate clips. Per-display files simplify playback compatibility but require shared clip identity and timestamps.
- **Hotplug and performance.** Bind selection to physical paths, reconcile topology updates and retire changed graphs. Canvas dimension or stream-set changes need a new epoch. Measure capture, GPU copy and encode utilization, VRAM, RAM and dropped frames on mixed-resolution monitors before enabling simultaneous capture.
- **Audio synchronization.** Use a common monotonic clock for video sources and the configured audio tracks. Define pacing for displays with different refresh rates, keyframe boundaries, and behavior when one display falls behind or disappears. A stitched output uses one shared audio timeline. Independent files or streams need a defined shared-track strategy and synchronized boundaries.

## Owner hardware acceptance

1. On Windows 10 and 11, enable Instant Replay and verify idle starts no graph. Launch a known game directly on each monitor in windowed and borderless modes. Confirm the game name and display in the status bar.
2. Move the game to the other monitor in both directions. Repeat with different resolutions and matching resolutions. Save after the transition and inspect the first and last video frames. Confirm only the new session is available, previous markers are cleared, and sound stays in sync.
3. Put Discord in focus on the other monitor and then over the game. Confirm the game identity and display remain stable. Visible windows on the captured display can appear in the clip.
4. Disconnect the game display during capture. Verify capture pauses even when Windows relocates the game. Reconnect and verify the current source before resuming. Repeat with a disconnected manual display.
5. Start manual capture on the selected display while a game runs elsewhere. Stop the override and verify that capture returns to the game's current display with a fresh buffer. Close the game and disable the master. Verify capture stops in both cases.
