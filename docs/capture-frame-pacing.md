# Capture frame pacing and encoding handoff

## Evidence and decision

The informal Marvel Rivals comparison at 3440×1440 showed about 160 game FPS with recording off and 133–140 with HEVC recording at about 60 FPS. Video Encode fell from about 37% at P4 to 17% at P2/P3 with no reported recovery in game FPS. The roughly 92% overall GPU reading is an overlay observation. These are different counters, and the runs lack matched frame-time traces. The root cause of the game FPS loss is still open.

Keep the public DDA/WGC capture paths and FFmpeg NVENC encoder for this workstream. The branch adds measurements at the existing call sites. It preserves frame selection, source transitions, GPU/CPU transfer choices, thread priorities, keyframes, replay insertion, and the Personal P2 default. There is no measured gameplay speedup from these changes.

## Where time can go

- QuickClip pulls DDA or WGC frames, maps them to its fixed frame grid, sends accepted frames to FFmpeg, drains packets, and inserts them into the replay ring from one video thread. Its local D3D11 scaler submits a video-processor blit before the frame-grid decision on scaled DDA. Native DDA has no local scaling blit. WGC scaling happens in the source filter. Media Foundation uses an explicit download and NV12 conversion path. The NVENC path has no explicit CPU readback.
- GPU surfaces are held by FFmpeg frame references and the scaler's output pool. The packet ring stores compressed video and audio packets, not textures. The video insertion timer includes the video-generation lock, cloning the packet, and taking the shared ring lock. Audio inserts into the same ring, and save snapshots clone packet references under the ring lock before muxing. Spikes in that timer can narrow an investigation to shared locking, but it does not identify which caller held a lock.
- The pinned FFmpeg NVENC source for `d4070a14ce` selects synchronous output mode and calls the bitstream lock with waiting allowed. QuickClip drains output on its capture thread. A long drain is therefore a candidate recorder stall, but a wall time alone cannot determine whether the hardware engine, driver, scheduling or host work caused it. NVIDIA documents both async completion events and a DirectX caveat when DXGI capture and bitstream locking move to different threads. Measure the drain before introducing a queue or SDK fork. [Pinned FFmpeg NVENC source](https://github.com/FFmpeg/FFmpeg/blob/d4070a14ce/libavcodec/nvenc.c), [NVIDIA NVENC threading guidance](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html)
- Video uses a normal worker thread and requests a 1 ms timer period for pacing. WASAPI source threads opt into the Audio MMCSS task. The audit found no reason to change priorities based on the available FPS or utilization readings. Capture and encode may compete with the game for graphics scheduling or memory bandwidth even with low Video Encode utilization.

## Reading the opt-in diagnostics

The existing five-second diagnostics switch now reports source, submitted and packet rates, same-slot rejects, and missing timeline slots. Same-slot rejects count frames discarded before submission. DDA repeats can carry fresh timestamps and remain in the submitted count. Counting repeated content or DDA acquisition coalescing would require source metadata. A gap on the output timeline does not itself identify dropped game presents.

Source wait is wall time in the FFmpeg sink call and includes pacing and work within the source graph. The accepted-frame pipeline covers the time from a successful pull through output handling. Local scale reports CPU-side wall time per scaled frame, including frames subsequently rejected by the timeline. Submit and output handling are per accepted frame. Output handling includes frame release, packet retrieval, and ring insertion. Replay insertion is shown separately per emitted packet. Source wait and submit include maxima for the sample window. These timers do not require a GPU fence or timestamp readback and cannot measure GPU execution. Benchmark JSON supplies process CPU, actual replay bytes, and UTC sample times. The legacy cumulative gap counter in benchmark JSON is DDA-only.

## Supervised A/B procedure

1. In a repeatable nonprivate game scene, run 15-second trials with recording off, native monitor DDA, and native game-window WGC. Keep resolution, refresh, FPS cap, scene, game settings, codec, recording FPS, preset and bitrate fixed wherever the comparison allows. Keep the overlays and audio setup constant. Use the actual backend and output size in diagnostics, especially when a game falls back to the monitor. Repeat at least three times and reverse the order. Compare P2 with P4 only within the same backend.
2. If an existing PresentMon console build is available and has trace access, set `$presentMonExe` to its path, `$gameProcessId` to the running game PID and `$caseName` to a unique trial label. Check its help for the listed switches. This captures process presentation events, without desktop pixels or audio. If it cannot start the trace, use the existing overlay and record that frame-time tracing was unavailable. [PresentMon console switches and metrics](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)

   ```powershell
   New-Item -ItemType Directory -Force .\.quickclip-local\frame-pacing | Out-Null
   & $presentMonExe --process_id $gameProcessId --session_name QuickClipFramePacing --no_track_input --date_time --timed 15 --terminate_after_timed --output_file ".\.quickclip-local\frame-pacing\$caseName.csv"
   ```

3. Compare median and 95th/99th percentile game frame intervals on the main swap chain. Keep presented intervals and displayed intervals separate, particularly on a 144 Hz monitor where the game can submit above refresh. Record 3D, Copy and Video Encode separately. Correlate time windows with recorder source wait, submit, drain, missed slots and actual replay bytes. If game pacing changes while recorder wall times remain low, a short existing GPU scheduling trace can test the copy/DWM hypothesis. Neither Task Manager utilization nor the game's PresentMon row directly times QuickClip's NVENC execution.
4. For a short video-only desktop diagnostic, quit the other recorder instances and run the existing bounded runner from a nonprivate scene. Run once per backend and bitrate. The command saves metrics only. It does not exercise game-window targeting or audio. Use `-AutoVideoBitrate` in place of `-VideoKbps` to use the High quality preset formula.

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\benchmark-video.ps1 -Build -CaptureDesktop -Seconds 10 -Fps 60 -Encoder hevc_nvenc -Preset p2 -Backend DesktopDuplication -VideoKbps 20000
   ```

The existing opt-in `Duplication_scales_on_GPU_and_saves_valid_video_only_clip` test also checks the new timing output and target bitrate, then decodes a short clip. Run that single test with `QUICKCLIP_TEST_CAPTURE=1` only while supervising a nonprivate desktop and with other recorders stopped. Leave the flag unset for the full suite. Keep trace CSVs, logs and temporary clips local.

## Target bitrate and rate-control contract

`RecordingPresets.VideoKbps(..., targetKbps: null)` keeps the existing Auto quality formula. An explicit target uses the same integer kbps from **500 through 250,000** for either monitor or window when the integration caller passes it. The shared cap matches the Auto ceiling and narrows the diagnostic runner's former 500,000 kbps cap. The benchmark uses the existing numeric native capture ABI and reports the resolved rate. The production Settings and Recorder paths still call Auto.

For integration, persist a nullable target and pass it to both recording bitrate call sites in `Recorder.cs` and the estimate in `SettingsView.xaml.cs`. Validate on edit and on load, show an estimated memory footprint for the selected duration and audio tracks, and apply changes at a capture generation boundary. At 250 Mbps and 300 seconds the nominal video payload alone is about 9.38 GB. The current time-based ring is not a byte cap. Before shipping user-controlled high-rate/long-duration combinations, account for actual memory headroom and verify a keyframe-aware byte bound, including when WGC stops delivering pictures while audio continues. Never present an estimate as a hard maximum.

| Rate control | Behavior and release constraint |
| --- | --- |
| Target VBR | NVENC currently uses target bitrate, a 1.5× peak setting and VBV size of two seconds at target, with no B frames. Preserve this policy. Actual bytes vary with content, and other encoder backends have their own behavior. |
| CBR | Useful when rate predictability matters, with compression and VBV tradeoffs on difficult scenes. Treat it as an explicit mode with codec capability checks. Exact byte pacing can depend on filler, headers and encoder behavior. |
| CQP | Quantizer-based control has content-dependent quality and size. It cannot supply a trustworthy fixed replay-size estimate. Require a verified encoder/driver combination, measured payload and a bounded ring before enabling it for continuous replay. Defer it here. |

Bundled FFmpeg listed `vbr`, `cbr` and `constqp`. The local driver accepted all three for H.264 and HEVC NVENC in 12-frame 640×360 synthetic encodes at P2/HQ. The test used 6 Mbps for VBR/CBR and QP 23 for CQP, with a null sink. This verifies initialization and short encode completion for those combinations. D3D11 acquisition, real-content quality, sustained replay behavior and other vendors' encoders were outside that probe. [FFmpeg NVENC options](https://ffmpeg.org/ffmpeg-codecs.html#NVENC-encoders)

## Future recording APIs

- **Replay hotkeys:** bind each action to a requested duration against the single retained ring. Use its available keyframe-aligned start, report the actual saved span, and share snapshot/mux logic across bindings. A 120-second action needs sufficient configured retention. Reject conflicting hotkeys without creating another capture session.
- **Full session:** spool compressed packets into bounded, recoverable segments with source-generation and stream metadata. Reserve disk budget, apply backpressure or stop with a visible reason on full disk, and finalize to a new path before publication. Preserve originals through crash recovery and only publish verified output.
- **Bookmarks:** store a capture generation plus monotonic capture time. Translate to a clip-relative timestamp when a snapshot's actual keyframe-aligned start is known. Mark expired events as outside the retained range.
- **Per-game profiles:** resolve the effective target, codec, bitrate, frame rate and audio policy before starting a generation. Surface buffer restarts for incompatible changes. Maintain consistent stream parameters per snapshot.
- **CPU and iGPU alternatives:** use a distinct opt-in encoder capability check. x264 needs readback/conversion and competes for CPU time. An iGPU can require cross-adapter transfers and synchronization, so verify format compatibility and matched game frame times before treating either as a performance improvement.

## Branch validation

- Base is published `5bc5d3a237ce39824006a76eb0f756d14fd753ef`. The full Personal suite passed 254 tests with 16 opt-in Windows tests skipped. The six synthetic NVENC checks above saved no media.
- The usual development executable was running. An isolated Personal Release output compiled with zero warnings or errors and passed the bundled capture engine, libmpv, FFmpeg and FFprobe checks. The active recorder was left running.
- The expanded timing output, live D3D11 frame pacing and matched gameplay A/B measurements still need the supervised runs above. Feature integration should retain the existing settings defaults and use the shared resolver for both capture paths and estimates.
