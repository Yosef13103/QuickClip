# Discord companion group capture (owner-approved implementation scope)

## Integration candidate checkpoint (2026-11-21)
This isolated branch implements qc_start_companion / qc_update_companion: authorized WGC HWND sources feed the existing QuickClip encoder, replay ring and one shared audio graph, without any desktop/monitor fallback. D3D11 shader compositor, stable canvas, maximum 4 windows / 16M source pixels, FPS capped to 60. WGC window source identity uses HWND, thread, PID, process creation time and closed events; invalid/revoked sessions fail closed, without recording another app. Game/manual desktop captures have priority. UI Settings > Companions provides Discord-specific opt-in, call/open/manual triggers, source status and privacy warnings. Save uses the Discord folder automatically. No per-popup audio duplication. Win10 system WGC capture borders may appear.

Evidence: native/C# builds and 42 focused tests have passed, zero failures. Standalone GPU proof 420/420 frames at 60 FPS, one NVENC encoder, zero CPU pixel readbacks and 7x25 phase RGB checks. This does NOT prove integrated QuickClip replay. A native generated-window buffer/save fixture is compiled but NOT run while Marvel Rivals is active (owner observed possible FPS interference). No native QuickClip MP4, media-track sync, real Discord window, update transition or game impact validation yet. Full regression, generated-window decode and owner acceptance remain required; no release or stable merge authorized.

Performance gates: idle/1/2/3/4 source CPU, memory, VRAM, copies, frame latency/drops, video engine utilization at 720p30 and 1080p60, compare when no game is active; only owner-authorized Marvel Rivals FPS and 1-percent lows comparison. Avoid a second QuickClip capture/encoder while game is active; optimize detector idle path.

### Persistent recording controls from checked-out Rewind
Rewind source at lib/src/ui/widgets/recorder_panel.dart (lines ~22-48, 126-245, 367, 420) explicitly rejects earlier permanent top/bottom control strips. Its compact navigation-rail status chip opens a panel with source selection, buffer length, Save clip and Record; tray reflects live state. A one-second ticker only runs during manual recording or buffer filling; the source documents ~45% Flutter app plus ~45% WindowServer CPU from a former continuously pulsing implementation. These measurements are Rewind/macOS-specific, not QuickClip measurements.
QuickClip already has compact persistent bottom status/Save. Proposed optional rail/tray popover exposes source, buffer, Save, companion control, and eventually true Start/Stop continuous recording without an always-on animation or a second audio graph. Continuous manual recording is distinct from replay saving and is not implemented here.

Discord only; no Zoom/Teams, no simultaneous game + companion video, no monitor composition. User accepted live observer and wants all Discord pop-outs (stream, camera, profile) recorded together. Explicit opt-in to all visible verified windows of one Discord edition, with a clear warning that this can include DMs/profiles. Windows rendered within another Discord window are already included in that window; independent top-level windows have independent WGC sources. Do not classify private content by title or scrape Discord internals. Later optional selected-window/layout controls; no guessing which pop-out is a stream by size alone.

## State and priority
Master off -> no detector or capture. Existing explicit manual desktop request retains priority; eligible game outranks companion even if game's display unavailable. Discord call mode default *when explicitly enabled*, optional while-open/manual (manual requires explicit request); per-edition identity, no implicit grant to different editions. Detector samples at ~1s when appropriate, single flight, monotonic age <=3s, unknown on stale/error, no audio/network payloads; >=2s positive and >=4s negative hysteresis. No-mic/denied call detection unproven, offer explicit alternatives. During leaving debounce keep only an already active call, revoke immediately on invalid source or permission. Preserve explicit user audio track selections; Sonar is not a requirement. Endpoint playback can include unrelated sound: label scope truthfully, no automatic microphone enable or process-loopback promises.

## Layout and bounded resources
One fixed session canvas (initial prototype 1280x720/60); one window fills canvas preserving aspect, multiple use stable main/side tiles. Suggested final layout: main/selected primary left ~65-70%, one secondary full-height right, two or three secondary stacked or grid, center fit with black gaps. Reorder only at explicit request, maintain existing tile order on new windows and close. Profile/camera/stream windows treated the same unless explicit per-window choice. No desktop background, no screenshot fallback. Minimized or not-ready tile black until fresh frame; close/revoke removes cached pixels. Do not reset replay or encoder when adding/removing/resizing a tile. Initial policy max 4 windows, prototype proven 3; cap is provisional, overflow must be visible and fail closed rather than silently omit windows. Benchmark before raising cap. Native target lease must handle HWND reuse, WGC Closed events, thread/PID/process creation time, current grant, generation and stale GPU frames; simple PID check insufficient.

## Remaining integration gate
Existing Engine::Start requires monitor and VideoLoop may fall back from a closed/failed window to monitor; never reuse that as companion start. Add dedicated group native source contract before graph startup, no monitor acquisition/fallback; separate source identity from output geometry, fixed hardware frame context and group updates serialized with generation, frame/publish checks and bounded stop/recovery. Integrate existing packet ring, encoder options, audio engine and replay receipt/sidecar Discord identity; no display-only save permission bypass. Suppress game/desktop-specific watchdog/flat-picture recovery for valid static/black tiles, but not source failure. Verify master/revoke/priority, known game return, no stale data, native teardown, multi-window resource bounds, actual replay mux and audio sync. Add settings only once functional backend available, explicit consent copy, companion status label, optional fallback modes. Test synthetic across 1/2/3/4 windows, rapid open/close, cross-adapter, minimize, resize/reorder, HWND reuse, revoked grant, stale sampling, actual owner-supervised Discord capture, non-Sonar and no mic, Windows 10 WGC border visible. No release until integrated and independently reviewed. Keep current development and production untouched until verified candidate.
