# Recording epochs — experimental branch

> **2026-11-22 live integration checkpoint:** The isolated `feat/recording-epochs` build now contains an experimental runtime path for **verified game recordings**: capture graph stop/format rotation seals decodable compressed packet epochs into a volatile, adaptive-budget archive; a following verified graph may retain those epochs; an explicit Save Clip can stage their MKV segments and normalize them with the current MP4. No media is continuously written to disk. The original no-epoch save remains unchanged. This code is **not merged into Development/Production and has no real GPU/game/permission-transition acceptance**. The historical research notes below describe the earlier pre-integration checkpoints.
>
> **Limits:** manual desktop and Discord companion epoch continuity, physical monitor disconnect/crash reconnection, rolling MKV crash recovery, sample-accurate real stem seams, GPU export/frame pacing, and user-facing gap policy are not accepted. The combined memory ceiling bounds retained compressed ring/archive packets, with short reclamation lag and additional in-flight/codec/GPU allocations outside that accounting. Every hardware and privacy acceptance gate remains required; no FPS guarantee is claimed. On older supported games/encoders, the routine codec selection remains unchanged.

Status (historical starting point): **isolated research and planning; NOT enabled at runtime**. Source branch `feat/recording-epochs` created from accepted `integration/development` at `66511a358277dab97c817c9c9532ab7b0afbe7e2`. No automatic merge to Development or Production. Owner wants this architecture for both game and Discord capture, including resolution changes, same-game monitor moves, brief display loss, game crashes, replay preservation, and future overlapping replay union.

## Verified starting point

- `src/QuickClip.Capture/Engine.h/Engine.cpp`: `PacketRing` is an in-memory deque of FFmpeg **encoded packet references** retained on a time window (plus ~2-second pre-roll); `Stats` counts packet bytes. Currently it has **no independent byte budget or persistence**. Its video packet sequence and source IDs survive changes *within the same Engine*; the ring object belongs to the Engine/capture graph.
- `src/QuickClip/Recording/RecordingLifecycle.cs`: changing desired activation (physical display, game identity) calls `StopGraph()`. An unauthorized/disconnected display cannot be used as an automatic fallback. `Recorder.cs:StopGraph` increments replay generation, calls `CaptureEngine.Stop()`, clears session ID/markers. The old graph's ring is gone. Cross-graph continuity is not currently supported.
- `Recorder.StartCore` uses a single fixed encoder/canvas per graph. Discord starts at 1920x1080 before applying global recording resolution, and `GroupCapture` fits window sources into that fixed canvas. Dynamic source dimensions do not dynamically change the encoded output dimensions.
- `ReplaySaveReceipt` provides session, first/last frame timestamps, source IDs, markers; a separate repo contract `docs/overlapping-replay-research.md` addresses exact interval union, packet proof, multitrack joins, and transactional publishing.

## Choice: RAM first, disk optional

Retain compressed packet rolling replay **in RAM** as the default for instant saving and zero sustained disk writes. Add an explicit byte budget alongside time retention; preserve a complete decodable GOP and fail closed on impossible constraints. At 30 Mbps, ~225 MB per minute of video before audio/pool overhead; no hard-coded assumption that Windows system disk is an SSD.

Optional crash-recoverable mode later: bounded disk-backed *encoded segments* with journal, not raw frames; choose storage location based on writable capacity, user preference, disk performance and error telemetry, not blindly the OS drive. Sequential writes are important for HDDs; SSD is preferable for frequent segment IO, but not required for standard RAM mode. Use low-disk guard, quotas, startup recovery/discard policy, crash consistency, archive exclusions, privacy and lifecycle tests. MKV or fragmented MP4 may improve **saved file** recovery; neither makes a volatile RAM replay survive a crash and neither fixes mixed codec dimensions.

## Capture-graph separation

Keep a logical replay **timeline** independent of encoder/capture graph lifetime. Each graph contributes a bounded encoded epoch with: session/source identity validated by current capture policy; unique graph/epoch ID; capture backend/physical display; start and end timestamps on a monotonic clock; frame dimensions and encoder/stream fingerprints; source/grant revisions; frame keyframes and audio track mapping; explicit gaps/discontinuities. Packet segments belong to this timeline; do not retain raw frames in bulk.

Source lifecycle rules:
- Same verified game moves to a different *authorized* monitor: after validating source/HWND/PID and display permissions, close one epoch/open another; retain older compressed packets until rolling window expires. No unauthorized desktop fallback or reuse of the old display's grant.
- Brief display disconnect: stop acquiring promptly; mark discontinuity; preserve already-buffered footage **only within retention and memory budgets**, resume only after current display grant is verified. Do not fabricate frames.
- Game crash/restart: do not silently continue capturing other windows. If reopened game is verified as same game identity and authorized source, a later epoch may join the logical session under explicit bounded recovery policy; record outage gap. Never attach a different game's frames to an old game replay. No unconditional infinite history retention.
- Discord call/window changes: continue respecting opt-in, call modes, game priority, live PID/HWND verification and multiwindow source scope.
- Rapid resize/drag: don't restart encoder for every pixel. Debounce and adopt a new canvas/epoch only for a stable material change; transient frames are fitted into current canvas. **This means short-lived higher source dimensions cannot be promised at native resolution until captured in a matching encoded epoch.** UI must not claim otherwise.

## Saved clip semantics

Select an exact replay interval based on retained encoded epochs (not session's historical maximum). Output dimensions come from the largest **encoded** epoch by pixel area (deterministic tie-break), subject to GPU/encoder budget. Other epochs uniformly scale-to-fit and center-pad (never stretch); optional crop/fill is a user-explicit export preference. If all retained epochs are 1080p, save 1080p. If a 3440x1440 epoch appears in the interval, use 3440x1440 and letterbox narrower epochs. Track explicit discontinuities; decide whether to omit gap or visibly disclose gap in export.

Fast packet remux only when **all** video/audio codec parameters, timebases, extradata, timestamps and decode dependencies permit it; do not infer correctness from successful muxing. Mixed-size/codec epochs require a bounded normalization pass and generally video re-encoding. Audio stem continuity, priming/padding, seeking, cancellation, low space and partial publication must be tested. For future overlapping clips, derive chronological **union** of verified session intervals, then normalize once per combined output. Preserve originals until staged output verified and journaled; never auto-delete uncertain legacy/edited/project-linked media.

## Phased acceptance

1. **Plan + unit tests (current initial milestone):** immutable epoch and interval model; select only retained intervals; reject mixed owners/overlaps; mark gaps; choose max encoded resolution; hard resource cap. No live capture changes.
2. **Provenance instrumentation:** bounded native graph/epoch events and packet metadata; synthetic feeds, no new per-frame logs; validate save receipt/markers across boundary.
3. **Ring lifetime isolation:** preserve compressed old-epoch packets across authorized graph recreation without capture mutex contention; limit bytes/time, preserve keyframes and all tracks.
4. **Mixed-resolution normalization:** staged output with hardware-aware sizing, FFprobe, decoded video/audio continuity and 1080/ultrawide change cases. Compare FPS, 1% lows, GPU, RAM and disk IO against current Development.
5. **Same-game monitor move/disconnect/crash recovery:** supervised real tests; zero leaks of wrong physical display or unauthorized source, truthful gap behavior. Manual desktop capture must not broaden automatically.
6. **Overlap union + opt-in disk persistence** as separate gated work, reusing the existing overlap provenance contract.

Do not alter released or Development recorder until all relevant gates pass. Preserve existing QuickClip UI/Discord behavior. No synthetic GPU stress required to prove the first phase.

## Implemented isolated spike (November 21, 2026)

New code on the experimental branch is functional but **not connected to normal recording**:

- `ReplayEpochPlanner` selects caller-labelled logical session intervals, rejects mixed session/scope labels, limits canvas pixels, returns explicit gaps, and determines the largest *encoded* epoch in the selected interval (not maximum ever seen). **These labels are not OS authorization proof**; verified live owner/display grants must be supplied and checked by the future capture integration.
- `ReplayEpochNormalizer` reads independently encoded on-disk epoch files (MP4 **or MKV**) using bundled FFprobe, validates actual video dimensions, slice coverage and compatible audio-track labels, and invokes bundled FFmpeg **without a shell**. It trims each epoch, changes its pixel *and sample* aspect ratios, uniformly scales/centers each image to the selected output canvas, joins the video and up to 16 separate audio streams in order, and creates one staged H.264/AAC MP4. Output is probed for dimensions, stream count and duration before atomic same-directory publication; failed/cancelled staging is cleaned up, original input segments remain unchanged. Actual output decoding is exercised by synthetic tests. The exporter currently uses software x264 **off the capture thread**, with a 32-epoch, 15-minute, 2-minute process timeout and 8192x4320 format ceilings. The default rejects discontinuities. An explicit `OmitMissingFootage` export policy allows concatenating only frames actually captured, reports the omitted duration in its result and file comment, and never invents intervening frames; the live UI/metadata still needs to disclose this before enabling it. This is **not** a live recording integration, and not a performance certification at 3440x1440/60 fps.
- Native `PacketRing` now accepts optional byte pressure in addition to time trimming; old packets are evicted, and saved snapshots still select a retained keyframe, never a mid-GOP start. Actual Engine construction provides a **startup-calculated memory budget** of min(total physical RAM/8, available physical RAM/3, 2GiB), floor 64MiB. Fixture-only ring constructor defaults to legacy 0 for unbounded tests. The budget is not recalculated during the recording; this does not yet solve surviving across graph resets. Under sustained high bitrates the replay can become shorter than the requested seconds. Current source remains experimental; user-facing quota warning/policy still needed before promotion.
- Added synthetic integration tests that produce real two-stem encoded video segments in MP4 and MKV, exercise differing dimensions, run normalization, validate final duration/streams, decode the result and verify source inputs were not modified. A separate set exercises native AVPacket memory pressure with real nonzero payload sizes, no GPU/capture/audio sources. One initial export run revealed mismatched sample aspect ratio and was corrected via `setsar=1`; a standalone native ring test exposed missing `CaptureEngine.Initialize` and was corrected. Failures were not suppressed.
- **Known gaps:** Capturing/retaining epoch packets across graphs, live graph/source authorization transitions, per-epoch audio sample-accurate continuity, packet provenance and gap handling, GPU-assisted normalization, isolated disk recovery, per-source resolution switching/debounce and resuming safely after source loss. In particular, `RecordingLifecycle` + `Recorder.StopGraph` currently destroy the native graph and reset the replay session; this user-facing behavior is unchanged. The exporter must not be connected until verified archive and authorization layers exist.

## Detached native encoded-epoch ownership (next isolated gate, 2026-11-21)

- New header-only `src/QuickClip.Capture/DetachedEpochArchive.h` owns independent AVPacket references **and copied AVCodecParameters/timebases**, so original graph-owned PacketRing snapshots and codec contexts can be destroyed after archiving. It records logical session, source-scope label, grant revision, epoch ID, local/global packet timestamps and original packet-source/sequence IDs. It rejects malformed packet metadata, missing initial video keyframe, wrong session or source-scope labels, nonmonotonic/overlapping graph epochs and duplicate/out-of-order epoch IDs. Completed epochs are evicted as entire units under byte/time quotas. Caller retains and frees source snapshots. It does not permit capture or perform authorization; scope strings and revisions are **metadata, not trustworthy proof of active HWND/PID/display consent**.
- `qc_test_detached_epoch_archive` is a synthetic exported C fixture in Api.cpp. It constructs two separately owned native PacketRings with video/audio packets, transfers packet snapshots + stream metadata into the detached archive, destroys both source rings and checks archive data survives. Negative cases reject different logical source/session and overlapping epochs; bounded case evicts oldest whole epoch. No GPU, audio capture, real games or user media.
- `tests/QuickClip.Tests/DetachedEpochArchiveTests.cs`: five scenarios with verified packet content/stream parameters plus invalid-input case. Focused strict Personal native/export/epoch suite: **15 passed, zero failed, zero skipped**. No live capture behavior changed.
- This is the resource-ownership foundation only. A user-authorized live graph transition must still transfer packets **before** the old graph is invalidated, validate live process/display permissions independently, map absolute QPC timestamps and audio layout, preserve safety against stale capture/device grants, and verify the final saved MP4. Current `Engine::Shared::InvalidateVideoLocked` clears the ring immediately, and normal `Recorder.StopGraph` destroys the graph. Neither path is changed by this header.

## Packet-to-media roundtrip and continuity policy (November 22, 2026)

Experimental code now exercises a complete **synthetic** encoded-packet path:

- `DetachedEpochArchive.cpp::WriteSegment` remuxes archived packet clones plus independently copied codec parameters/timebases and track titles to a Matroska segment. The writer explicitly refuses an existing output path. It is a **test-only adapter**, not a release-ready transactional media publisher.
- Exported native fixture `qc_test_detached_epoch_media_roundtrip` demuxes two short, locally generated H.264/AAC MP4 files, transfers their encoded packets into two independent short-lived native `PacketRing` owners, detaches those packets with codec metadata, destroys the original ring owners, then writes two MKVs from the surviving detached archive. The C# integration test decodes each MKV, normalizes 640×360 + 960×400 segments into one 960×400 MP4, retains **two separate audio stems**, marks/omits one second of unavailable video through the explicit gap policy and decodes every resulting media stream. Original fixture files remain intact. No physical game, desktop, microphone, production media or GPU capture is touched.
- `ReplayEpochContinuity` is a pure **game-only** comparison of two previously independently verified source observations. It allows the same live process moving between separately authorized physical displays or recreating its window, and permits verified same-game process reacquisition only when explicitly enabled and within 10 seconds by default. Different catalog game IDs/verified executable paths, expiration/out-of-order transitions, master switch changes, failed owner checks, revoked display permission, **explicit permission-generation changes** and recording-disable generation changes refuse continuity. The permission generation is a future integration contract and **is not currently available from the app's per-display grant policy**; do not reuse the recording-disable revision as a substitute or connect this policy to live capture until revocation increments are wired. **This is not live OS verification**: caller must independently recheck PID, process start, HWND ownership, catalog eligibility, display identity and current permissions on every transition, and clear the archive immediately on revocation. Discord/manual continuity is intentionally not enabled by this policy yet.
- The native archive now rejects a change in its explicit permission/revocation generation as well as session identity and scope label; an extra synthetic negative fixture covers that refusal. This field must have consistent semantics when wired to live authorization; arbitrary increment-per-graph values are not valid.
- Focused verification after the native provenance guard: **31 passed, 0 failed, 0 skipped**, 0 build warnings/errors. Full suite is a separate integration gate. None of this is wired to `Recorder.StopGraph`, native live save or capture permissions.

**Not delivered:** live cross-graph retention, actual resolution changes inside active Discord/game capture, GPU export benchmarking, gap-aware Gallery/UI, crash-recoverable disk buffers, persistent replay after machine failure, concurrent save/lifecycle tests, sample-accurate real microphone sync and overlapping replay union. A full capture integration must preserve revoked-source privacy and have explicit user-visible acceptance before promotion. A valid synthetic media file does not prove real-time capture stability.

## Live grant-generation foundation (November 22, 2026)

Experimental AppSettings now maintains `CapturePermissionRevision`, a runtime-only monotonic counter incremented on recording disable, physical-display default permission/allowlist/denylist mutation, and Discord grant/mode/mirror changes. A revoke-then-reallow sequence **cannot** restore an old encoded epoch under the same generation; failed-setting rollback also conservatively invalidates existing detached history. This counter is not persisted in JSON. A capture-graph restart or application process restart is a fresh lifetime and must establish a new proof.

`ReplayEpochLiveProof.TryCreate` constructs a *read-only* game-only continuity proof by revalidating current HWND/PID/start time, current exact game catalog eligibility and executable path, resolved physical monitor identity, current display consent, master switch and stable permission/disable revisions **before and after the check**. It returns no proof if source state cannot be verified. Synthetic tests cover source move between permitted monitors, blocked/disconnected display, process/catalog rejection and revoke-then-reallow during observation.

This new proof builder remains **dormant** and does not yet connect to Recorder, Native Engine, or automatic Discord capture. Production callbacks must use authoritative `GameDetector.IsCurrent`, `GameCatalogRuntime.Match`, `Monitors.ForWindow`, `Monitors.List` under the recorder's serialized authorization gate; injecting test callbacks or static labels does not grant consent. Permission generation alone never proves a capture is currently authorized.

Next safe milestone: instrument per-graph codec/audio/packet fingerprints and synchronized stop/start timeline events; attach a native archive only after source grant validation and stop/save concurrency tests. Do not let detached buffers survive manual stop, master-off or source revocation; a transient display interruption preserves bytes only while their grant and retention quota remain valid.

## Live graph implementation review — key lifecycle hazard

The native recorder currently **destroys history before managed StopGraph in some cases**:

- `Engine::Shared::InvalidateVideoLocked` clears `ring` immediately when video source loss is detected (e.g. display disconnect). This can happen before `RecordingLifecycle.Reconcile` sees and stops the graph.
- `VideoLoop` also calls `ring.Clear()` under `videoLock + infoLock` when a new video encoder's parameters differ from the previous stream. Thus resizing or changing encoder formats can erase earlier valid footage within the same Engine before any managed epoch handoff.
- Ordinary `Recorder.StopGraph` destroys the Engine; and `Engine::Save` snapshots packets/codec state for only one configuration. Merely detaching on `qc_stop` cannot recover already-cleared packets.
- `Engine::AudioLoop` uses independently owned encoder contexts and optionally an extra hybrid-composite track; any retained epoch must capture its actual stream count, timebases, codec extradata, titles, and packet origins along with its video generation.

**Next architecture gate:** pair each encoded `PacketRing` with immutable stream metadata, and rotate the pair *at native format/source discontinuity* rather than clearing the ring. Prefer an ownership transfer/swap of a bounded compressed packet-ring object into a short-lived, uncommitted epoch quarantine so capture thread stays nonblocking. Managed source authorization and stable permission revision must validate the proposed continuation; if revoked or unverifiable, immediately discard quarantined history. Rotation, ownership release, grants, and save-in-flight need race/leak/deadlock tests before this is wired to QuickClip's real capture engine. Special handling is required for a genuine display disconnect, where the source may vanish without advance notification; never fabricate missing frames or capture a replacement display without permission.

**Do not** implement naive `StopGraph → Snapshot` as the full solution: it misses native ring clear, can stall graph teardown and might preserve media from a revoked source. A file container switch alone cannot solve this either. This is the active next design problem; native AVPacket epoch media roundtrip and managed grant-proof tests already exist.
