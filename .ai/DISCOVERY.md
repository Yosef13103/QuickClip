# Wave 2 — game discovery and activation contract

## D1. Desired UX and boundaries (W2-G1/G2/G3)
The Games page is the control center: automatic discovery switch, Scan now, Add Game, libraries/launchers with support/access state, source enable/disable, searchable game list with immediate capture enable/disable, useful name and source, details showing match/why and effective overrides. Preserve existing owner-approved styles and controls; do not redesign Wave 1 UI. Common work: one game library approval, no manual approval of every legitimate renderer within that library. Exact executable and shortcut add must work even without heuristic engine metadata; an incorrect EXE product name must not become the game label. Unknown/ambiguous entries remain explainable and manageable. Manual adds do not inflate scanned counts. Do not conflate display permission with game permission.

### Identity and runtime policy
Trace the actual `GameCatalogIndex`, `GameCatalogService`, `GameDiscoveryCoordinator`, `Recording/CaptureSourcePolicy`, `Recording/Recorder` and settings persistence/tests (paths are hints). Map discovery → source provenance → stable title/install identity → executable candidates → user policy → live window verification → capture arbitration → actual source grant → acquisition. Code may differ; follow real call chain. Do not redesign all layers if local repair suffices. At v1.1.0 verified source already has `Recording/ForegroundGameHandoff.cs` (PreferForeground), `Recorder.cs` calls `ObserveEligibleGame` and checks authorization during activation, and `CaptureSourcePolicy.cs` revalidates retained matches. This is evidence of existing mechanisms, not proof of correct real behavior. Inspect and test these before changing arbitration; full catalog path resolution remains W2-A.

| Input | Eligibility expectation (still requires live authorized source) |
|---|---|
| Explicit exact EXE or resolved shortcut chosen for capture | Exact install/path + verified live HWND/PID wins over missing/low renderer confidence or poor metadata; explicit deny wins; genuinely ambiguous/sensitive identity requires explanation, not implicit promotion. |
| Explicit enabled game folder/library | Legitimate game binaries belonging to known install or scoped game identity eligible without another renderer-confidence hurdle. No automatic rule for every EXE under a broad root. Use install evidence, precise paths, known non-game roles, corroborated launch handoff, actual live main game window. |
| Enabled supported launcher library | Valid installed-game metadata and matching scoped executable/window; existing Steam/Epic launch evidence preserved. No directory-name-only identity. |
| Disabled game/excluded root/executable | Deny automatic game capture even if another overlapping source finds it. |
| Unapproved unknown / helper / updater / launcher / crash reporter / installer / 7za / browser / companion | No automatic game capture from discovery or basename alone. Explicit selection of ambiguous helper as a game must not be silently accepted; surface conflict and offer safe precise choice, never treat Discord Update.exe as general game. |

Renderer/engine scoring may rank candidates or explain ambiguity; it is not new consent and must not veto a deliberately authorized, verified game. Do not replace one hardcoded heuristic with another. Exact approvals are canonical scoped paths, not basenames or global process rules. Preserve aliases and explicit exclusions across rescan/update. Handle path case, separator, junction/reparse, UNC/offline volumes, stale PID, process relaunch, launcher-to-game transition. Never execute scanned binaries or expand roots via untrusted shortcut/glob. Unknown identity or lost display fails closed. Avoid indiscriminate polling and expensive per-process I/O. Tests must cover positive and negative cases including previously fixed `7za.exe`.

## D2. Source arbitration (W2-G2)
Master off stops capture and invalidates manual grant. Master on without eligible authorized game waits without active encoding. Manual desktop session supersedes automatic policy until explicitly stopped; changed display requires verified explicit grant and new replay epoch. For automatic: current valid game stays selected through ordinary Discord/browser/desktop focus. If a *different* verified eligible game becomes foreground, switch to it (debounce only to prevent transient churn; do not pin first forever). If active game closes, loses source, becomes excluded or no longer eligible, re-evaluate authorized candidates or wait. No arbitrary fallback to unrelated desktop. Follow verified active game's monitor; apply existing game display exclusion/grant every transition. Distinguish game identity, acquisition target and epoch: same-display changes may have continuous physical graph only if source attribution/privacy/ring contract remains correct; never mix unrelated game footage into mislabeled replay, define epoch behavior and test it. Full display is still full display, even with game labels. No game hook, companion capture or multi-monitor composite here.

Owner fixture history: Nidhogg → tModLoader → Nidhogg failed to switch previously until first process closed; Nidhogg monitor movement and Discord non-hijack once passed. Reproduce against current SHA; test foreground switching, overlapping windows, ordinary focus loss, minimization/nonrendering, close/reopen, move monitor, excluded monitor, unplug, stale HWND/PID and capture recovery. For osu!lazer, Marvel Rivals and portable games, inspect real identity in owner-supervised session only; don't conclude based on game names.

## D3. Incremental catalog (W2-G3)
Audit existing 15-minute coordinator timer, bounded resumable slices, scan-request equality and snapshot cadence before touching. Desired behavior: add/edit/enable/remove **one** source affects only that source (except dedup/shared provenance reconciliation). Periodic refresh can scan due enabled sources; coalesce concurrent changes; cancellation preserves already committed data. No permanent cap on large collections; bounded page/slice work and memory, cursor resume while process alive; explicit incomplete state if restart cannot resume. Maintain previous catalog on partial/failed/offline scan; delete a source's claim only when authoritative successful scan or explicit removal permits; preserve other source claims, stable IDs and all user overrides/manual rows. Avoid retaining capture eligibility from removed/disabled sources without another valid grant. Test overlapping manual/launcher/folder identities, changed paths, duplicate canonical paths, failed parse, stale generations and add/remove mid-scan. Do not migrate entire catalog blindly; migrations reversible/compatible.

Products counts are separate: unique known games, unique successfully discovered in applicable scan, manual entries, cached/unverified retained entries, per-source scanned counts, progress work units. Define overlaps explicitly; no summing overlapping rows and calling it total. Report inaccessible vs missing vs unsupported vs canceled; no fake zero-result success. Retain legacy explicit non-default depth choices. Normal scan publication bounded (old policy <=1/s; verify source); flush on completion/pause. No recursive whole-disk walk, unauthorized roots, repo/clip archive scan or endless UI updates. Scoped globs require preview, finite work/depth and confirmation; no global regex. Stable identity method must not depend solely on display name. Store path/source provenance without exposing private inventories.

The milestone 2 candidate stores one claim per configured folder, explicit Steam library or automatic launcher source in existing profile JSON. Automatic Steam still refreshes its discovered library set as one provider. A scope and scan-option signature guard publication, and each source owns its cursor. Changing a title or override leaves scan scheduling alone. A preview publishes positive evidence as each install completes. Paths from unfinished installs are display only. A failed source can retain completed installs and cached display information. Progress that adds no verified evidence leaves the recorder's executable index in place.

The legacy flat snapshot enters the new projection as unverified display data. An authoritative applicable scan retires its old copy. Verified provider identities can coalesce with folder claims at an exact shared install path. The projection prefers the stable provider key, and associated folder rules and explicit denies continue to apply. The same title can have live and cached paths from separate sources. Manual entries and overrides remain independent of source cache records. A full scan can report fewer newly discovered titles than the total catalog because retained and manual records are counted separately.

Keep metadata access local, read-only and bounded. Preserve ordinary filesystem permissions and WindowsApps ACLs.
