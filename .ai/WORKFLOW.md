# Execution: one parent, scoped delegation, checkpoints

## Parent workflow
1. Read index + selected ledger entries and contract sections. Preflight Q1. Review previous checkpoint only if SHA/candidate still relevant. Verify access to native subagents and current model/effort; do not modify unrelated `.codex` settings or revive old role prompts. If stale global/nested instructions conflict, stop or explicitly reconcile with owner; serial parent remains fully supported.
2. Identify dependency-ready tasks in the approved prompt scope. Produce short map of actual call paths + gap/test plan; user prompt authorizes bounded implementation, not release. Reuse discovered map, no fresh whole-repo scan between neighboring tasks. If a substantial architecture, dependency, security, data migration or new scope decision remains, checkpoint with recommendation; don't improvise widening authority.
3. Optional read-only agents (0–2 concurrently): one identity/arbitration trace, one incremental/provider seam or adversarial review. Give task ID, baseline, exact paths/symbol questions, contract section, max ~25 lines result (findings/evidence/gaps/tests). No edits/builds/commits from explorers. Independent reviewer later sees diff/contract, not transcript. Parent normally sole writer; if delegating writer, transfer lease explicitly and wait until done; never simultaneous writers or shared build output conflicts. Agent role is an instruction, not sandbox guarantee. If isolation unavailable default to one parent.
4. Implement narrow coherent slice with focused tests. Validate and make checkpoint; only commit/push/open PR if explicitly allowed by owner/run scope (push/PR separate from commits). PR base custom/main; stacked unmerged code dependencies use same authorized candidate or explicit stacked base plan with final integration against custom/main. Do not falsely mark dependency stable when only in candidate. Prefer first discovery candidate one coherent branch/PR with reviewable commits; later native/updater changes separate. Transition to new branch safely only when checkout clean and approved.
5. At milestone run full checks/review as QUALITY. Stop at agreed milestone; report tasks/gates, branch/SHA, commands/results, actual limitations, next step. Don't loop on unavailable CI/hardware. Separate pending hardware from safe independent tasks. On budget/context issues write short ignored checkpoint and stop.

## Effort and token use
- Parent High for discovery decisions, concurrency and source policy; Medium for straightforward bounded UI/docs/test fixtures; Extra High only complex native ring race/capture architecture, if supported and evidence justifies. Read-only explorer Low/Medium usually sufficient; independent reviewer Medium/High on risk. No forced model IDs, no assumed per-thread controls. Check actual app/version capability; no need to configure native agent TOML for this kit.
- Each subagent reconsumes context. Prefer single writer with persistent context, known file/symbols, compact `git diff` and test summaries, task IDs and line ranges. Do not paste full migration JSON, source files, or entire future roadmap into every task. Research source snippets centrally; no repeated CI polls. External research ChatGPT, local execution Codex, hardware owner. Avoid repeated full tests across tiny edits; don't skip coherent integration gates. Cache behavior service-controlled, no guaranteed savings.
- Checkpoint format (`.quickclip-local/agent/checkpoint.md`, ignored): active milestone/IDs; exact base and candidate branch/SHA or dirty state; files changed/why; completed vs pending gates; tests/results and evidence refs; blockers/next exact actions; approval scope. Board is canonical shared status; checkpoint is local resume pointer only. No raw session IDs/secrets or private paths in tracked files. Start new parent only if needed; never reuse active CLI/App thread from another process.

## Suggested execution batches (not automatic dispatch)
- 01 discovery: W2-A, G1, G2, G3; G4 read-only in parallel if useful. Deliver working integrated candidate, not 6 chat threads. If scope too large checkpoint after G1/G2. 02 discovery verify: finish bounded missing tasks, G4 decision, approved G5 provider subset, G6 integration/owner script; split provider work if it needs dependency approval or more context. Keep broader reliability out of discovery unless directly blocking.
- Then W2-R1 targeted regression audit and W2-P baseline; W2-R2 real reproduced issues only; W2-D duration native isolated; W2-L logging separate; W2-U safe updater separate. W2-Z wave closure. Independent work may move while owner gates pending but no release without acceptance. Do not force two prompts for entire wave. W3/4 activate by owner after W2 closure, refresh board with selected research tasks.
